# Permission Handler — Pitfalls Catalog

| # | Symptom | Cause | Fix | Source |
|---|---|---|---|---|
| 1 | iOS app crashes silently the first time camera is called | `NSCameraUsageDescription` missing from Info.plist | Add the key with a specific usage string | [Apple Camera UsageDescription](https://developer.apple.com/documentation/bundleresources/information_property_list/nscamerausagedescription) |
| 2 | Android 13+ device — POST_NOTIFICATIONS dialog never shows | `compileSdk` / `targetSdk` < 33 — Android 13 runtime permission only enforced at SDK 33+ | Bump `targetSdkVersion >= 33` in `android/app/build.gradle` | [Android 13 notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission) |
| 3 | `permanentlyDenied` user → `permission.request()` returns the same status, no system dialog | Apple/Google policy: 2nd permanent denial sticks; you can only deep-link to settings | Detect `isPermanentlyDenied` → show modal with `openAppSettings()` button | [permission_handler docs](https://pub.dev/packages/permission_handler) |
| 4 | "Photos limited" — user picked 5 photos, app sees only those, but UI says "no photos" | Android 14+ / iOS 14+ partial photo access. `status.isGranted == false`, but `status.isLimited == true` | Treat `isLimited` as "allowed but partial"; build UI that works with subset; offer "Add more" button | [Android partial photo access](https://developer.android.com/about/versions/14/changes/partial-photo-video-access) |
| 5 | Permission blast at launch (5 prompts in a row) → user denies all reflexively | Calling `Permission.X.request()` from `main()` / first frame for every permission | Just-in-time pattern: ask at the moment of need + with explanation (soft-ask) | this skill's own decision tree |
| 6 | Android: `requestPermissions()` returns instantly with denied — no system dialog | Activity not visible (called from background isolate / pre-`runApp`) | Permission requests must come from foreground activity, post-`runApp` | [Android runtime permissions](https://developer.android.com/training/permissions/requesting) |
| 7 | Status returned is stale (settings changed while app in background) | Provider value cached; not re-fetched on app resume | Listen to `WidgetsBindingObserver.didChangeAppLifecycleState` → invalidate provider on resume | [Flutter app lifecycle](https://api.flutter.dev/flutter/widgets/WidgetsBindingObserver-class.html) |
| 8 | Apple Reject 5.1.1 — purpose string too vague | "For a better experience" / "to use this feature" | Be specific: what data, what it enables. Match the actual API calls | [Apple privacy reject reasons](https://developer.apple.com/app-store/review/guidelines/#privacy) |
| 9 | Permission opens twice in a row | Race: `request()` called from two widgets (e.g., parent + child both watch) | Centralize in `PermissionService` + Riverpod provider (single in-flight); call from ONE place | this skill's pattern |
| 10 | iOS "Location always" requested without "When in use" first | iOS requires sequential escalation: WhenInUse first, then Always | Two-step: `Permission.locationWhenInUse.request()` → on grant → `Permission.locationAlways.request()` | [Apple Core Location](https://developer.apple.com/documentation/corelocation) |
