# Secure Storage — Pitfalls Catalog

14 entries from `flutter_secure_storage` GitHub issues, Apple Developer Forum, Android Developers docs.

| # | Symptom | Cause | Fix | Source |
|---|---|---|---|---|
| 1 | Tokens persist after iOS app uninstall and a fresh install logs the previous user back in | iOS Keychain is device-scoped, not app-scoped; survives uninstall by design | First-launch sentinel in `shared_preferences` (which IS cleared on uninstall) → if missing, `deleteAll()` then set. See [snippets/fresh_install_wipe.dart](snippets/fresh_install_wipe.dart) | [dev.to](https://dev.to/isurujn/beware-of-fluttersecurestorage-on-ios-m6e), [Apple forum](https://developer.apple.com/forums/thread/36442) |
| 2 | Tokens lost after iCloud device migration / restore | Default `first_unlock` keys participate in Keychain backup/restore; if RSA private key cannot be re-derived, value becomes unreadable | Use `first_unlock_this_device` / `unlocked_this_device` for tokens you do NOT want migrated | [Issue #284](https://github.com/juliansteenbakker/flutter_secure_storage/issues/284) |
| 3 | `BadPaddingException` on Android `read()` after app upgrade | Keystore key invalidated (rotated, lockscreen credentials changed, factory reset of secure HW), or migration interrupted | Catch exception, `deleteAll()`, force re-auth; v10 default `migrateWithBackup: true` reduces this | [Medium fix guide](https://msanjana.medium.com/how-to-fix-flutter-flutter-secure-storage-exception-encountered-read-javax-crypto-badpaddingex-fc3ee5fede36) |
| 4 | App crashes on Android 14 release builds reading old EncryptedSharedPreferences | Jetpack Security `androidx.security:security-crypto` deprecated April 2025; combined with R8 obfuscation strips required classes | Migrate to v10 default cipher (`encryptedSharedPreferences` flag will be removed in v11); add ProGuard rules for `androidx.security.crypto.**` if staying on legacy | [Issue #690](https://github.com/juliansteenbakker/flutter_secure_storage/issues/690) |
| 5 | `read()` returns null on iOS 16.3+ even with same key written moments earlier | Mismatched accessibility level between write and read calls | Pin a single `IOSOptions(accessibility: ...)` in a const provider; never mix levels for the same key | [Issue #524](https://github.com/juliansteenbakker/flutter_secure_storage/issues/524) |
| 6 | Concurrent `write()` calls race and one value is dropped | No internal serialization on writes | Wrap writes in a `Mutex`; or batch via single repository entry-point | [Pub README](https://pub.dev/packages/flutter_secure_storage) |
| 7 | Returns null on Android emulator (works on device) | Emulators without Google Play / lacking secure HW; older AVD images cannot create Keystore key | Test on physical device; pre-create a fallback emulator profile with API 30+ Google Play image | [LeanCode glossary](https://leancode.co/glossary/secure-storage-in-flutter) |
| 8 | "Keychain item already exists" / OSStatus -25299 on overwrite | Existing item with different access control attributes blocks write | Delete first, then write; or call `write(value: null)` to clear before re-set | community |
| 9 | Biometric prompt shows but `read()` throws after 5 failed attempts | Android biometric lockout (30s soft / permanent until passcode) | Catch `LockedOutException` / `PermanentlyLockedOutException`; fallback to passcode via `local_auth` `useErrorDialogs:true` | [Ostorlab biometric guide](https://blog.ostorlab.co/secure-mobile-biometric-authentication.html) |
| 10 | Storing a 100KB JSON payload returns generic write error on iOS | iOS Keychain individual item limit ~4 KB (some sources cite 8KB practical) | Encrypt+store payload elsewhere (file system); keep only a small key in Keychain | [Apple keychain docs](https://developer.apple.com/documentation/security/keychain_services) |
| 11 | Biometric protection lost after user enrolls a new fingerprint | Android `setUserAuthenticationRequired(true)` keys are invalidated when biometric set changes | Detect `KeyPermanentlyInvalidatedException`, drop key + force re-login; document UX | [Android Keystore docs](https://developer.android.com/training/articles/keystore) |
| 12 | Refresh token replay: backend rejects rotated token, user kicked out at random | Two parallel API calls each triggered a refresh; first succeeds, second's response stomps the new token with a now-revoked one | Mutex around refresh (see SecureTokenRepository); ALSO server-side: rotation should accept previous token within a short grace window | [vibe-studio session mgmt](https://vibe-studio.ai/insights/implementing-secure-session-management-with-refresh-tokens-in-flutter) |
| 13 | Logout leaves app "remembered" — biometric still unlocks the cleared user | `deleteAll()` not invoked, or only `accessToken` cleared while biometric-bound `refreshToken` remains | Logout MUST call `_storage.deleteAll()` and invalidate biometric keys | [LeanCode glossary](https://leancode.co/glossary/secure-storage-in-flutter) |
| 14 | Plaintext password stored "for biometric auto-login" | Anti-pattern — many tutorials show this | Store the **refresh token** instead; never store passwords/PINs in any form | [Ostorlab guide](https://blog.ostorlab.co/secure-mobile-biometric-authentication.html) |
